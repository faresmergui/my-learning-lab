**EC2** (Elastic Compute Cloud) loue des machines virtuelles à la seconde. C'est le service le plus ancien d'AWS et celui sur lequel reposent beaucoup d'autres (ECS, EKS, EMR). Pour l'examen, il faut savoir choisir un type d'instance, préparer une image, configurer le démarrage et placer les instances.

> **Les outils cités dans cette fiche.**
> - **instance** : une machine virtuelle EC2.
> - **AMI** (Amazon Machine Image) : l'image disque d'où démarre une instance.
> - **user data** : un script lancé au premier démarrage, lu par **cloud-init** (l'outil standard d'initialisation des machines cloud).
> - **Graviton** : les processeurs ARM conçus par AWS, environ 20 % moins chers à performance égale.
> - **EBS** : le disque réseau persistant d'une instance (fiche Stockage bloc). **instance store** : un disque local éphémère.
> - **IMDS** (Instance Metadata Service) : le service joignable à `169.254.169.254` qui donne à l'instance sa configuration et ses identifiants temporaires.
> - **EC2 Image Builder** et **Packer** : des outils qui fabriquent des AMI automatiquement.
> - **Nitro** : le matériel et l'hyperviseur d'AWS ; les instances récentes en dépendent.
> - **ECS** : le service d'exécution de conteneurs d'AWS.
> - **EKS** : le service Kubernetes managé d'AWS.
> - **cache** : une copie rapide de données souvent demandées, pour éviter de les recalculer ou de les relire.
> - **GPU** : le processeur graphique, qui fait énormément de calculs en parallèle (IA, rendu).
> - **IA** : intelligence artificielle.
> - **AZ** : une zone de disponibilité : un ou plusieurs datacenters indépendants dans une région.
> - **latence** : le délai entre une demande et sa réponse.
> - **chiffrement** : transformer une donnée pour qu'elle soit illisible sans la clé.

## Choisir un type d'instance

```
m7g.large
│││ └── taille : nano, micro, small, medium, large, xlarge, 2xlarge…
││└──── attributs : g = Graviton, i = Intel, a = AMD, d = disque local, n = réseau rapide
│└───── génération : plus récent = souvent meilleur rapport prix/performance
└────── famille
```

| Famille | Profil | Exemple d'usage |
| --- | --- | --- |
| `t` | burstable : crédits CPU, pas cher | petits serveurs, dev |
| `m` | équilibré | applis web, la plupart des services |
| `c` | calcul | encodage, batch, serveurs de jeu |
| `r`, `x` | mémoire | bases en mémoire, caches, analytics |
| `i`, `d` | disques locaux NVMe | bases NoSQL, entrepôts de données |
| `p`, `g`, `inf`, `trn` | accélérateurs (GPU, puces d'IA) | apprentissage automatique |

Les instances `t` accumulent des **crédits CPU** quand elles sont peu utilisées et les dépensent en pic. Une `t3` qui tourne à fond en permanence est bridée (ou facturée en plus en mode `unlimited`) : il faut alors une `m`.

## Les images (AMI)

Une AMI contient le disque système et les réglages de démarrage. Trois sources :

- AMI publiques d'AWS et des éditeurs (Amazon Linux, Ubuntu, Red Hat, Windows) ;
- AWS Marketplace (logiciels prêts, avec licence) ;
- tes **propres AMI** (« golden images ») construites avec Image Builder ou Packer, avec tes logiciels et ton durcissement.

Une AMI est **régionale** et peut être partagée avec d'autres comptes. Pour un plan de reprise dans une autre région, on la **copie** là-bas à l'avance.

## Le démarrage : user data

```bash
#!/bin/bash
dnf install -y nginx
aws s3 cp s3://shop-config/nginx.conf /etc/nginx/nginx.conf
systemctl enable --now nginx
```

Le script tourne une seule fois, en root, au premier démarrage. Sa sortie est dans `/var/log/cloud-init-output.log`. Bonne pratique : l'AMI contient les logiciels, les user data seulement ce qui change d'une instance à l'autre.

## Les métadonnées et IMDSv2

```bash
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 300")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/placement/availability-zone
```

Avec **IMDSv2 obligatoire** (option `HttpTokens=required`), une simple requête GET ne suffit plus : la plupart des failles SSRF (une appli poussée à appeler une URL choisie par l'attaquant) ne peuvent plus voler les identifiants du rôle. On l'exige sur toutes les instances.

## Le stockage d'une instance

| | EBS | Instance store |
| --- | --- | --- |
| où | disque réseau dans la même AZ | disque physique du serveur |
| survit à l'arrêt | oui | **non** |
| snapshot | oui | non |
| performance | bonne à très bonne | la meilleure |

## Les placement groups

| Type | Principe | Pour |
| --- | --- | --- |
| **cluster** | toutes proches, même AZ | calcul haute performance, latence minimale |
| **spread** | chacune sur un matériel distinct (7 max par AZ) | quelques instances critiques à séparer |
| **partition** | groupes de racks isolés | systèmes distribués conscients des racks (Kafka, Cassandra) |

## Le cycle de vie

- **stop** : l'instance s'arrête, le disque EBS est gardé, on ne paie plus le calcul ; l'instance peut redémarrer sur un autre hôte (IP publique changée, sauf Elastic IP).
- **hibernate** : la RAM est écrite sur le disque EBS chiffré ; au redémarrage, les processus reprennent où ils étaient.
- **terminate** : l'instance est détruite ; le volume racine aussi par défaut (`DeleteOnTermination`).

Les modèles de prix (à la demande, Savings Plans, Spot) sont dans la fiche sur les coûts.

> **À retenir.** Un type d'instance se lit famille, génération, attributs, taille ; `t` pour les petits besoins irréguliers, `m` par défaut. L'AMI porte les logiciels, les user data la configuration du premier démarrage. IMDSv2 obligatoire partout. L'instance store est rapide mais effacé à l'arrêt. Placement cluster pour la latence, spread pour séparer, partition pour les systèmes distribués.
